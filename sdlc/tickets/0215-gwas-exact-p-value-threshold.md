# 0215 — Return exact GWAS p-value threshold results in native p-value order

Status: OPEN.

Milestone: 4

Depends on: 0205
Depends on: 0230
Depends on: 0234

## Outcome

`search gwas --p-value THRESHOLD` with any selector is exact, not page-scoped. `search gwas` has no sort option, so every threshold search uses the native p-value-ascending order. A row whose p value equals the threshold qualifies. Each further page is a continuation step, offered only while every row so far qualifies. Rows arrive in that order, so the command returns rows until the first row above the threshold and stops; it continues to the next source page only while every row so far qualifies. It reports a qualifying total only when it reached the end. Any other sort with `--p-value` is a usage error. A page whose rows all qualify carries a continuation that keeps the selectors, the order and the threshold; a page that reaches the first row above the threshold, or the source's last row, carries no continuation and states the qualifying total. A page that has not reached the end states that the qualifying total is unknown and never relabels the source total or the rows seen as that total.

- Why: the 0.9 `--p-value` filtered a bounded prefix locally, and the GWAS ruling replaces that with an exact threshold that the native p-value-ascending order makes possible without a whole-catalog scan.
- Starts from: the `--p-value` bullet of the GWAS rulings in `decisions/2026-10-26-protein-pathway-study-rulings.md`, which wins over gwas.md's page-scoped proposal; 0205's threshold page-boundary witness; 0234's adapter, paging and continuation; 0230's exact p-value type.
- Rules: the threshold parses to the exact p-value type before I/O, and a value that is not a finite probability is a usage error. A row qualifies when its exact p value is at or below the threshold, compared by mantissa and exponent with no float rounding, so an underflowing p value still compares correctly. A row above the threshold is never returned. Rows after the first row above the threshold are never read or returned, and no further source page is requested. Each source page in the walk keeps the order check; a reply out of p-value-ascending order fails with a problem rather than returning a wrong total. A walk across pages keeps the received identities and rejects a duplicate or mismatched page. A threshold with no qualifying first row returns a successful zero with a total of zero. The existing adapter deadline and source category stay unchanged.
- Proof: outside-in cases first, watched to fail. Before threshold code, one bounded keyless pm job captures each case's exact request once, with zero retries, and records the replies. A PMID 17529967 case with a threshold between 6112's and 6113's p values asserts three rows, no continuation and a qualifying total of three; a threshold above every row asserts a full first page with a continuation and an unknown total, then a second page that reaches the source's last row and states the total; 0205's page-boundary witness asserts a first page whose rows all qualify, a continuation, and a later page that stops at the first row above the threshold with the total stated; a threshold below the first row asserts a successful zero. Synthetic cases cover a threshold equal to a row's p value, an underflowing p value, a reply out of order, and `--p-value` with another sort as a usage error with zero requests. Recorded 429, 500, timeout and broken-body cases on a later page assert a failed outcome with source and terms and never a qualifying total. Each case gets a ceiling at measured size plus 15 percent, recorded in gwas.md. Real replies replay from outside the repo through `--cases DIR`, and synthetic replies prove the remaining mechanics. Then make landing-gate runs through pm job.
