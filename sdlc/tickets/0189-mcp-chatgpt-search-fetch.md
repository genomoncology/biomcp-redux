# 0189 — Add ChatGPT-compatible search and fetch MCP tools over the CLI

Status: OPEN.

Milestone: 4

## Outcome

The MCP server lists `search` and `fetch` beside the main `biomcp` tool. `search(query)` runs the CLI's own `search` command and returns its rows as results, each with an `id`, `title` and `url`. `fetch(id)` runs the CLI's own `get` command for that `id` and returns the record's `id`, `title`, Markdown text, `url` and metadata. Both tools reach their answers only through the same command functions as the main tool, so their output cannot drift from the CLI.

- Why: Ian amended the one-tool decision on 2026-10-25. OpenAI's current MCP docs (https://developers.openai.com/api/docs/mcp) require `search` and `fetch` for deep research and company knowledge, with an output schema and matching structured and JSON text content. Its custom server guide (https://developers.openai.com/api/docs/guides/custom-mcp-server) says other custom plugins do not require them. 0.9 shipped these tools for ChatGPT users (public issues 21 and 37).
- Starts from: the amended decision `decisions/2026-10-23-mcp-is-one-tool-over-the-cli.md`; the MCP tool and protocol code; the Markdown view; 0.9's search and fetch tools; OpenAI's current published MCP and deep research tool contract, read by the developer and cited in architecture.md before code.
- Rules: if the query's first word names a BioMCP entity (such as `trial`, `variant` or `gene`), `search` runs `search ENTITY REST`; otherwise it runs `search article QUERY`. Each result's `id` is the exact `get` argument list for that row, such as `article 17611497`, and `fetch` accepts only such an id. Anything else is the same usage error the CLI gives. The `url` is the record's source URL and is never empty. The default page size and ceilings are the CLI's. No new search logic, ranking, synonym expansion or entity guessing beyond the first-word rule. Source terms, problems and outcomes appear in the metadata as the CLI reports them. The tool schemas follow OpenAI's published shapes, including `outputSchema` and `structuredContent` matching the JSON text content, and are checked by the existing schema compatibility check.
- Proof: outside-in cases first, replaying existing captures: `search` with an article query, with `trial ...` and with `variant ...`; `fetch` of an article, a trial and a variant id taken from those results; a bad id; and `tools/list` showing the three tools within a measured description ceiling. Each case asserts that the wrapper's output matches the CLI output for the same command. No provider call. Then make landing-gate runs through pm job.
- PM ruling 2026-10-25: `search` emits a result only for a row that has both an exact `get` target and a source-backed record URL; it never invents an id or citation. Aggregate and relation rows without them, such as VAERS summaries and FDA companion relations, are left out of `results`, so a query may return zero results. Beside `results`, the output carries one `metadata` object, declared in this tool's own output schema: the full CLI envelope for the command it ran (rows, source outcomes, terms and problems) and the count of rows left out with the note that they are available through the `biomcp` tool. Each result object keeps exactly the official `id`, `title` and `url`. A query is never rejected only because its rows are not fetchable. One case covers a VAERS summary search returning zero results with the envelope and omitted count in metadata.
