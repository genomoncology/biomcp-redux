# 0035 — Answer search article with plain PubMed from a stored pool

Status: OPEN.

Milestone: 1

## Outcome

`biomcp search article [TEXT] [--gene INPUT] [--variant TEXT] [--disease TEXT] [--drug TEXT]` returns PubMed's own relevance order for the exact term it echoes, from a pool built once over PubMed's whole 9,999 window, with stable pages that a warm read serves without a request, a total, a truncation flag and a notice naming words PubMed did not find, through the CLI and the one MCP tool.

- Starts from: article.md sections 3 (PubMed rows), 5 (the default, `--gene` term, pools and pages, what the response says, biodata types) and 8 (cases 1–7, 18, 30); architecture 3.6, 3.8, 5.4, 6.7, 6.8, 6.10, 6.11, 7.1–7.3 and 10.1 as amended on main; `gene::resolve` in biomcp-query; biodata `PageInfo`, `SourceOutcome`, `StepKind`, `ErrorEnvelope` and `Source::PubMed`; `SecretName::NcbiApiKey` in biomcp-fetch; binary config.rs (the OncoKB key pattern), grammar.rs, spell.rs and command.rs; runner mod.rs and assertions.rs, which have no `follow`, `walk`, `unique` or `includes_all_of` yet; `ReplayCache` and `--case-cache`, which the runner already passes, so a pool written by one step is readable by the next.

- PM decision: 2026-10-24. `ArticleSearch` holds `text`, `source` (a list that accepts only `pubmed` here, default `[pubmed]`), `sort` (accepts only `rank` here, default `rank`), `gene`, `variant`, `disease`, `drug`, `limit` (1 to 50, default 10), `offset` and `pool`, so the query echo names the sources and the order as article.md says; later tickets widen the two lists. The term is the gene group, then TEXT, `--variant`, `--disease` and `--drug` joined by single spaces in that order, with ` AND ` after the group when anything follows. The group is the approved symbol, the input as typed and every previous symbol, deduplicated without case, in parentheses joined by ` OR ` when it holds more than one name. `--gene` resolves through `gene::resolve`: an ambiguous input runs no search and returns up to five disambiguate steps that rerun the search with each candidate's HGNC ID; a withdrawn or unknown input runs no search and answers status absent. A search needs TEXT or a filter.
- PM decision: 2026-10-24. biodata adds `Pmid`, `Pmcid` and `Doi` (article.md section 5 rules, DOI compared and hashed without ASCII case), `PublicationType` with PubMed's clinical types mapped and funding types dropped without a problem, `ArticleHeader` (`biodata.article_header/1`), `ArticleItem { header }` and `ArticlePage` (`biomcp.article_page/1`). `PageInfo` gains optional `pool` (id, size, created, expires) and `truncated`. `SourceOutcome` gains optional `term`, `count`, `fetched` and `notices`; the one notice kind here is `not_found_words` with PubMed's words, and it leaves the state ok. `StepKind` gains `restart`. The error envelope gains code `pool.expired` and an optional `next` holding the restart step.
- PM decision: 2026-10-24. The PubMed adapter declares source key `ncbi-eutils` at 3 per second and 10 with `keys.ncbi_api_key` or `NCBI_API_KEY`, following the OncoKB key pattern, and sends `tool=biomcp` on every call. A configured `ncbi_email` is passed from config through `Ctx` as an argument and sent as `email`; without it no `email` is sent. ESearch and ESummary replies stay fresh for one day, because they carry retraction status. The pool lives in the store module of biomcp-query (`pool`, `pool_current`, `pool_item` from architecture 7.1) in the same SQLite file as the reply cache, including the case-cache directory's file; a temporary replay cache gives a temporary store. A pool expires after 24 hours. Page headers come from one ESummary call when a page is first read and are stored on its items. A PMID that ESummary does not describe is dropped from the page with a problem. A failed ESummary leaves the stored pool unchanged and answers that page failed with a fresh step that rereads it with `--pool`.
