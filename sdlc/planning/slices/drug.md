# Drug slice investigation and proposed design

This design starts from `ecef1096239f8aeee8fcc6cbefc5720e89506035` and follows steps 1 to 4 of [the slice method](../slices.md). It serves cancer-care drug identity, authorization, label, target, biomarker-evidence and interaction questions. It proposes retrieval of attributed source facts. It authorizes no treatment interpretation, product code, new public service, or release. The PM reviews this design before filing implementation tickets.

## 2. Source findings and identity

The request plan uses twelve generic names, each shared by two clinical questions, plus Gleevec, Herceptin and Enhertu as brand identity controls. Each applicable source receives its own declared query; sources do not share an invented universal search language. A source that supplies no join identifier stays unjoinable. Source request identities, retrieval dates, bodies, byte counts, hashes and timings remain in the external evidence manifest. Reused bodies are local delivery of those original captures, not fresh provider responses.

## 3. What would delight the agent

1. **First question.** `search drug Keytruda --source mychem` returns candidates and exact next commands. MyChem is the one default search source because all twelve generic queries and three brand queries returned native candidates; it supplies identity cross-references without mandatory regulator fan-out. Omitted `--source` means only MyChem and is echoed. The agent chooses every other source explicitly.
2. **Smallest header.** One source's native ID, source name, display name, identity level, available source molecule/product type and document URL. No authorization event, full label or cross-provider product pick.
3. **Next steps.** Native-ID get, exact documented cross-reference, named label text, source targets/indications, source-scoped regulator detail and the named DDInter interactions get section. No shortage section is offered while deferred.
4. **Exact identifiers.** Published ChEMBL, MyChem document, SPL set/version, application/product number, EMA record, DDInter and CIViC therapy/profile IDs. Source remains a separate option, not an invented ID prefix.
5. **Disagreements.** Keep D06 dates by source/date role, D23 historical positive versus withdrawal document, and separate products in D04. No merged approval status or vote.
6. **Empty versus failure.** E01 is actual source-local zero; F01 is synthetic failed transport. Neither implies absence of clinical therapy, approval or interaction risk.
7. **Cost.** Default search calls one source. Explicit sections use their declared source; bundles are local and never auto-refresh during reads. Measured direct request costs remain above; valid 0.9 timing is unmeasured.
8. **Stop early.** A selected identity card answers identity only; the next named section answers the clinical fact. Native counts and exact next steps expose bounded pages.
9. **Trust.** Preserve revision, retrieval date, identity level, source terms, indication context and source-local completeness. OncoKB therapy-level next steps stay with the keyed variant source.

## 4. Proposed types, schema and commands

These are design names, not implemented contracts. `biodata` owns neutral identifiers and domain records without I/O or consumer imports. `biomcp-types` owns requests, source selection, envelopes, paging, cards, sections, caps and typed next steps. Reuse existing checked strings, dates, URLs, attribution and section outcomes. Generate schema from the types once. Proposed consumer schemas are `biomcp.drug_page/1`, `biomcp.drug_card/1`, `biomcp.drug_label/1`, `biomcp.drug_targets/1`, `biomcp.drug_indications/1`, `biomcp.drug_civic/1`, `biomcp.drug_approvals/1`, `biomcp.drug_regulatory/1` and `biomcp.drug_interactions/1`. Reuse the existing shared `biomcp.sync/2` receipt rather than inventing a drug sync schema. These names do not change any schema in this design-only ticket.

Domain records are `DrugIdentity`, `DrugIdentityRelation`, `DrugProduct`, `DrugLabelReference`, `DrugLabelSection`, `DrugTargetRelation`, `DrugIndicationClaim`, `DrugInteractionClaim` and source-scoped `AuthorizationEvent`. An authorization event preserves its own native regulator record, date roles, jurisdiction and original status. It is never a header/card field. DDInter models only the captured pair IDs, names and native level; it does not invent mechanism/management prose absent from the CSV. Existing CIViC structures retain complete therapy and molecular-profile context. No WHO/FDA-orphan/DGIdb runtime type is added for this bank.

### Header and card fields

The outer envelope reuses `schema`, exact echoed `query`, overall result state, source outcomes/terms, problems and typed `next`. These are consumer fields. A source candidate header contains only `id` in published form, `source`, source-native `name`, `identity_level`, optional native `type`, and optional source record URL. Every value is attributed to that one source. `identity_level` comes from the documented endpoint or record type, never from the shape of an identifier or another field. If the endpoint/record type does not establish the level, it remains unknown.

An exact-ID card adds only available source-native alternate names, source-native identifier cross-references with their relation/provenance, parent/product/formulation links explicitly stated by that source, record version/update/retrieval metadata, and available named sections/next actions. It carries no authorization events, universal approval flag/date, full label text, default interaction rows, inferred biomarker meaning or arbitrary merged target list. `targets` and `indications` are named sections. A regulator card is still an identity card; its native authorization facts appear only under its explicit regulatory/approvals section.

### Structural risks and outside-in cases

The main risks are restated identifier mappings, inferred product merges, stale positive approval records, unshared bundle replacement, and proving a hand-written projection rather than the shipped artifact. Keep each source mapping in its owning adapter, generate schemas/help from one contract and compare returned IDs before cache admission. Pin outside-in cases to D01–D24 and the actual source requests; add actual E01 empty plus explicitly synthetic F01 failure, 429, timeout, broken JSON and mismatched identity. Each filter needs its own source-native known-positive capture. A field absent from the public tier makes its section unsupported, rather than an empty list. Two concurrent readers and one bundle replacement must observe a complete old or new batch. Installed-package proof belongs to implementation/release work, not this investigation.
