# Release channels

BioMCP 1.0 keeps every 0.9 distribution name. GenomOncology owns publication for all channels. Its release operator publishes only after Ian approves the release. Local artifact production grants no permission to upload, deploy, change a registry entry or move a release pointer.

| Channel | Artifact and platforms | Publisher and destination | How a 0.9 user moves |
| --- | --- | --- | --- |
| PyPI `biomcp-cli` | Platform wheels containing the native executable for Linux x86_64 and arm64, macOS x86_64 and arm64, and Windows x86_64. | GenomOncology's PyPI release operator publishes `biomcp-cli`. | Upgrade the same package with the existing package manager. Both `biomcp` and `biomcp-cli` launch the candidate executable. Keep `serve` in stdio client configuration. |
| `https://biomcp.org/install.sh` | Download installer and checksummed native release archives for Linux and macOS on x86_64 and arm64, and Windows x86_64 through MSYS, MINGW or Cygwin shells using its ZIP archive. | GenomOncology's site and GitHub release operator publishes the installer and archives to the existing site and `genomoncology/biomcp` release. | Rerun the installer for the approved version in the existing install directory. Retain the public download interface. The local `release/install.sh` accepts a supplied archive, checksum and destination; publication must provide the public download wrapper and retain Windows shell ZIP extraction. |
| Homebrew `biomcp` | Formula in `genomoncology/homebrew-biomcp`, selecting a checksummed macOS arm64 or x86_64 archive. | GenomOncology's tap release operator updates the existing tap after the archives are public. | Keep the existing tap and run `brew upgrade biomcp`. The local producer's file URL is a rehearsal input; the published formula must use release URLs. |
| GHCR `ghcr.io/genomoncology/biomcp` | Container image for Linux amd64 and arm64. | GenomOncology's container release operator publishes the version tag and moves `latest` only after release approval and both platform checks. | Pull the approved version from the same image name. The image entry point remains `biomcp`; use `serve` for stdio or the approved HTTP arguments. |
| Desktop extension `biomcp` | Platform-specific `.mcpb` archive containing `manifest.json` and the matching native executable. Preserve the existing macOS and Windows platforms. The local producer can also create a Linux bundle; that does not establish desktop client support. | GenomOncology's desktop extension release operator supplies the bundles to the existing directory or manual installation channel. | Update the extension through its existing distribution path. The manifest still starts the bundled executable with `serve`. Replace old per-tool client bindings with the single `biomcp` tool. Reconfigure credentials using the upgrade note. |
| MCP registry `io.github.genomoncology/biomcp` | Versioned `server.json` selecting the `biomcp-cli` PyPI package and stdio `serve`. Platforms follow the published wheels. | GenomOncology's registry release operator updates the existing entry after the matching wheels are public. | Refresh the same registry entry. Keep the package identifier and `serve` argument. The registry-selected executable and normal CLI use the same candidate bytes. |

## Production and qualification

The 0.9 sources are `genomoncology/biomcp`'s `install.sh`, `Formula/biomcp.rb`, `Dockerfile`, `manifest.json`, `server.json`, and `.github/workflows/release.yml`. They establish the channel names and platform families above. The 1.0 local producers live in [release/](../../../release/), [manifest.json](../../../manifest.json) and [server.json](../../../server.json). They derive versions from Cargo. They do not publish or reproduce the entire 0.9 publisher workflow.

Run `make release-artifacts` through the job service on the release candidate. The install gate exercises the wheel, supplied-archive installer, local formula where Homebrew exists, container, desktop manifest command and registry-selected package command outside the checkout. It checks the installed executable, MCP lifecycle, replay and concurrent ordinary-cache use. Preserve explicit deferred results when a native platform or Homebrew is unavailable. Native platform execution and installed HTTP checks belong to the installed-platform rehearsal; a generated manifest or cross-build cannot replace them.

Before publication, build each promised native artifact and complete the installed-platform rehearsal. Prepare and check the public installer wrapper, including Windows shell ZIP extraction, checksums, release URLs, macOS formula, image tags, desktop bundles and registry payload from that same approved candidate. Validate each public interface without publishing. Then obtain Ian's release approval before any service write. Publish dependencies before their consumers: archives before installer and formula; wheels before registry metadata. Keep old versioned releases available. Do not move `latest` until the approved version passes the release checks.

Read the [0.9 upgrade note](upgrade.md) before changing client configuration. Its generated command list comes from the same slice accounting as the roadmap ledger. `make docs-check` rejects drift in either generated view. Slices without closed accounting remain undecided; this plan does not approve their removal.
