# BioMCP

A clean rebuild of BioMCP on the biodata layer. When it is ready, its history replaces the biomcp repository's, keeping that repository's stars and releases.

`make landing-gate` runs formatting, lint, dependency policy and one instrumented workspace test suite. `make test` runs the ordinary suite for development. Coverage includes the CLI and MCP child processes and the public library contracts. The denominator contains product Rust source; test targets, generated output and build scripts are excluded.

The build machine needs `cargo-llvm-cov` and the pinned toolchain's LLVM tools. `make coverage` follows the [external-test sequence](https://github.com/taiki-e/cargo-llvm-cov#get-coverage-of-external-tests) and prints the total. The floor lives in `coverage.floor`; the threshold allows the architecture's counting tolerance. Only the lander raises an established floor. A failed suite has no complete coverage result.

`make unreached` lists missing lines from the existing profiles without rerunning tests. `sh scripts/coverage.sh report` repeats only the concise floor check. These commands require profiles from a successful coverage run in the same checkout. Full reports remain separate from the routine gate.

`biomcp health` prints the implemented sources, publisher terms, enabled state and bounded source reachability. It reports missing keys and disabled sources as skipped. It does not synchronize local bundles. `--disable-sources pubmed,restricted` disables individual source names or the `restricted` and `noncommercial` groups. The same setting lives in the JSON configuration as `"disable_sources": ["pubmed", "restricted"]`. Configuration and command settings combine by union; a command cannot enable a source disabled by configuration. Disabled sources cannot supply cached replies or restore stored article pools. Publisher terms remain authoritative, and the source category grants no rights in individual records.

BioMCP uses platform TLS trust roots. To add a company certificate authority, set `ca_bundle` in the config file to a PEM file. This adds certificates for every source and keeps verification enabled. `biomcp help network ca_bundle` explains this setting.

Set `proxy` in the config file to an HTTP or HTTPS proxy URL to use that route for every source. Otherwise BioMCP reads `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`. Each proxy variable applies to its own scheme. `NO_PROXY` accepts comma-separated exact hosts or IPs, `.domain`, `*.domain`, optional ports, and `*`. An explicit config proxy overrides these environment settings. `biomcp help network proxy` explains routing.
`make release-artifacts` runs through `pm job` before releases and at the end of the milestone. It builds local wheels, binary archives, a local Homebrew formula and container images. It installs the candidate outside the checkout and checks embedded assets, the MCP lifecycle, replay and concurrent processes sharing an ordinary cache. It publishes nothing. The wheel inspector binds the installed binary to Cargo's profile and candidate bytes. Linux builds execute inside the declared manylinux floor and inspect ELF version requirements before writing wheel tags. Both container architectures execute. Missing native platform or Homebrew execution remains a release rehearsal requirement; the gate never labels it passed. Windows execution requires a Windows machine. HTTP checks join this gate when the HTTP server exists.

The desktop extension and MCP registry templates keep their existing channel names. The local producer supplies their version from Cargo, bundles only the matching platform's executable, and writes registry metadata that selects the local `biomcp-cli` wheel and `serve` entry point. The gate installs each bundle in a fresh directory and starts its manifest command. It installs the registry-selected wheel in a separate environment with a standard offline wheel installer and starts its declared command. It does not contact a desktop client or publish to the registry.

The wheel exposes `biomcp` and the registry's package entry point, `biomcp-cli`, from the same candidate bytes. Registry-selected invocation therefore works after a normal offline package installation. Registry metadata follows the [official package schema](https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json); desktop bundle installation follows the [MCPB manifest command rules](https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md).
